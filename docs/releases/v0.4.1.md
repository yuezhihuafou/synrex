# Synrex v0.4.1 — security and release-integrity update

These are the release notes for the v0.4.1 security patch. The exact release archive, tag and verification evidence are authoritative; a document alone does not establish publication.

This patch is intended for self-hosted single-owner installations. Linux remains the primary supported production platform; macOS and Windows receive native packaging and portable installation acceptance, but are not guaranteed to match all Linux shell and sandbox behavior.

## Changes

- Refresh vulnerable direct and transitive dependencies, including the MCP SDK/server/client packages, HTTP proxy/IP handling, `undici`, `zod`, `node-forge`, and parser dependencies.
- Add blocking dependency-security and native macOS/Windows package-install checks before stable publication.
- Include the immutable pnpm dependency lock in release archives and machine-readable SBOM, plus archive checksums and build provenance.
- Document supported platforms, vulnerability reporting, setup, safe upgrade and rollback boundaries.

## Compatibility

- Node.js >=22.19 and <27; Node 24 is used for native macOS/Windows acceptance.
- The `synrex` CLI and legacy `devspace` aliases, single Owner OAuth identity, MCP URL, existing persistent SQLite and workspaces remain unchanged.
- Existing experimental Windows peers and gateway nodes are **not** automatically upgraded. Keep exactly one writable Owner and avoid duplicate peer identities.
- No API/host-side automatic wake-up of ChatGPT reasoning is claimed after a terminated chat session.

## Upgrade

1. Back up Owner configuration, secrets and SQLite using a consistent online snapshot. Record active systemd `ExecStart` and keep the previous immutable release.
2. Download the release archive and `SHA256SUMS` from this exact tagged GitHub Release. Verify SHA-256 before using the portable staging command.
3. Stage in a new user-controlled prefix using `node deploy/portable-install.mjs --stage --version 0.4.1 --source ./synrex-0.4.1.tgz --sha256 SHA256_FROM_RELEASE`. This does **not** replace a live service.
4. Test `--version`, `doctor`, authenticated OAuth/MCP and, if applicable, independent Console health. Explicitly activate the portable pointer, or follow the pinned Owner promotion path documented in `docs/platform/SINGLE_OWNER_SELF_HOSTED.md`.
5. Verify the active production manifest, public OAuth discovery, authorized tools, backup integrity, and rollback procedure. Never change the public issuer or copy the Owner SQLite to another peer.

## Rollback

- Portable launcher: `node deploy/portable-install.mjs --rollback` restores the prior verified pointer if one exists; it does not automatically roll back running system services.
- Pinned Linux Owner: follow the backed-up, guarded immutable-release activation process; restore the previous service manifest and compatible SQLite snapshot only when necessary and authorized.
- Do not delete or overwrite the old release during installation. A successful Git push or Release does not mean production has been updated.

## Known limits

- Native Mac/Windows CI validates installation and package entrypoints, not every Linux-only sandbox, shell/TTY behavior or real physical peer.
- Windows legacy peer and offline gateway migration are separate live operations.
- The ordinary ChatGPT UI interruption/reconnect journey needs a real client session; the durable execution and workflow-checkpoint mechanism does not resume model inference on its own.

## Verification

For release acceptance use the exact source SHA, `main` CI run, release workflow run, SHA256SUMS, SBOM, provenance attestation, native OS tests and pinned production manifest. Do not treat documentation or synthetic tests as substitutes for an observed live deployment.
